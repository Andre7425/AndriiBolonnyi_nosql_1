# Аналітика треків Spotify (MongoDB)

Цей репозиторій містить скрипти для завантаження, трансформації та аналізу датасету треків Spotify за допомогою бази даних MongoDB. Проєкт демонструє розгортання БД у хмарі, побудову документо-орієнтованої схеми, складні аналітичні агрегації та оптимізацію запитів через індексування.

---

## 1. Налаштування оточення та запуск проєкту

### Підготовка середовища
1. Переконайтеся, що встановлено **Python 3.8+** та **MongoDB Shell (mongosh)**.
2. Встановіть необхідні залежності з файлу `requirements.txt`:
   ```bash
   pip install -r requirements.txt
   ```
3. Створіть у корені проєкту файл `.env` та додайте ваш рядок підключення до MongoDB Atlas:
   ```env
   MONGO_URI=mongodb+srv://<username>:<password>@<cluster_address>/?retryWrites=true&w=majority
   ```
4. Завантажте **Spotify Tracks Dataset** із Kaggle та помістіть файл `dataset.csv` у корінь проєкту.

### Порядок запуску скриптів
Проєкт виконується строго послідовно:
1. **Завантаження сирих даних:** `python scripts/01_load_data.py` (створює колекцію `tracks_raw`).
2. **Трансформація схеми:** `mongosh "ВАШ_MONGO_URI" --file scripts/02_transform.js` (формує фіна колекцію `tracks`).
3. **Аналітика та індекси:** * `mongosh "ВАШ_MONGO_URI" --file queries/part2_queries.js`
   * `mongosh "ВАШ_MONGO_URI" --file queries/part3_aggregations.js`
   * `mongosh "ВАШ_MONGO_URI" --file queries/part4_indexes.js`

## 2. Схема даних (Колекція `tracks`)

Сирі плоскі дані були трансформовані у гнучкий документо-орієнтований формат. 

**Опис ключових полів:**
* `track_id`, `track_name`, `album_name`, `track_genre`: Основна текстова інформація.
* `explicit` (Boolean): Наявність нецензурного контенту.
* `popularity` (Integer): Рівень популярності (0-100).
* `artists` (Array): Масив імен виконавців.
* `audio_features` (Object): Вкладений документ, що містить акустичні характеристики (`danceability`, `energy`, `tempo` тощо).
* `duration_sec` (Double): Тривалість у секундах.
* `popularity_tier` (String): Обчислюваний рівень популярності (`high`, `medium`, `low`).

**Приклад документа:**
```json
{
  "track_id": "5SuO8XG6Z36OCC7gSgXpBq",
  "track_name": "Vampire",
  "album_name": "GUTS",
  "explicit": true,
  "popularity": 84,
  "track_genre": "pop",
  "artists": ["Olivia Rodrigo"],
  "audio_features": {
    "danceability": 0.511,
    "energy": 0.532,
    "loudness": -5.745,
    "speechiness": 0.056,
    "acousticness": 0.169,
    "instrumentalness": 0.0,
    "liveness": 0.311,
    "valence": 0.322,
    "tempo": 137.942,
    "key": 5,
    "mode": 1,
    "time_signature": 4
  },
  "duration_sec": 219.7,
  "popularity_tier": "high"
}
```

## 3. Теоретичні обґрунтування та аналіз

### Частина 1. Проєктування схеми

**1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?**
* **Чому винесено:** Це робиться для логічного групування (Data Cohesion). Всі ці параметри описують єдину сутність — "акустичний профіль".
* **Коли вигідно:** Коли дані мають чітку ієрархію і часто запитуються разом. Завдяки вкладеності ми можемо витягнути всі фічі однією командою в проєкції (`{ audio_features: 1 }`).
* **Коли створює проблеми:** Коли рівень вкладеності перевищує 2-3 рівні. Це подовжує синтаксис запитів (через крапкову нотацію `audio_features.danceability`) та ускладнює створення індексів за внутрішніми полями.

**2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?**
* **Чому:** Рядок (`"Artist A; Artist B"`) неподільний. Шукати в ньому довелося б через повільні регулярні вирази, які погано працюють з індексами.
* **Що спрощується:** Завдяки масиву `["Artist A", "Artist B"]` пошук стає прямим (`find({ artists: "Artist A" })`). Стають доступними потужні оператори: `$in` (пошук за списком), `$all` (спільні треки), `$size` (сольні треки). На масив можна створити швидкий Multikey Index.

**3. Що таке `$out` і чим він відрізняється від `$merge`? Коли використовувати кожен?**
* **`$out`:** Повністю перезаписує колекцію (або створює нову). Використовується для первинного наповнення бази, повних ETL-процесів або створення тимчасових зрізів даних.
* **`$merge`:** Об'єднує результати з існуючою колекцією інкрементально. Вміє оновлювати існуючі документи або додавати нові за визначеним ключем. Використовується для регулярного оновлення баз (наприклад, щоденне додавання нових треків) без перерахунку всієї колекції.

### Частина 2. Запити до даних

**1. Для чого використовується інструкція `$unwind`?**
Вона "розгортає" масив. Якщо трек має 3 артистів, `$unwind` створить 3 копії документа, де в полі масиву буде стояти по одному виконавцю. Це критично необхідно для групування (`$group`), щоб правильно порахувати індивідуальну статистику для кожного окремого виконавця.

**2. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?**
* **`$stdDevPop` (Population):** Рахує стандартне відхилення для *усієї генеральної сукупності* наявних даних. Використано нами, оскільки ми аналізували всю наявну базу треків.
* **`$stdDevSamp` (Sample):** Використовується для оцінки відхилення за *обмеженою вибіркою*, застосовуючи математичну корекцію для екстраполяції на всю групу.

### Частина 3. Аналітика через Aggregation Pipeline

**1. У запиті 1 (Топ виконавців) ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1 або підвищити до 50?**
* **Зниження до 1:** Топ заповнять "артисти одного хіта" (один завантажений трек випадково отримав популярність 100). Це статистична аномалія, що руйнує аналітику стабільності.
* **Підвищення до 50:** Зникнуть популярні сучасні артисти з невеликою дискографією. Залишаться лише ветерани індустрії, але їхня середня популярність впаде через ефект "регресії до середнього" (неможливо випустити 50+ хітів підряд).

**2. У запиті 3 ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50?**
Так. До рейтингу зможуть потрапити нішеві мікро-жанри, які містять невелику кількість екстремально танцювальних треків, створених кількома авторами. Поріг у 100 треків діє як фільтр надійності, відсікаючи статистичний шум.

## 4. Індекси та оптимізація продуктивності

### Завдання 4.1. Аналіз запиту та індексація (Правило ESR)
**Запит:** Пошук треків `track_genre: "pop"` з високим `danceability`, відсортованих за спаданням `popularity`.

* **ДО створення індексу (`explain`):**
  * `stage`: `"SORT"` (вкладена стадія `"COLLSCAN"`).
  * `totalDocsExamined`: `113999`.
  * *Пояснення:* База виконувала повне сканування диска, після чого робила важке сортування всіх знайдених документів в оперативній пам'яті.

* **Створення індексу:**
  Використано правило **ESR (Equality, Sort, Range)**:
  ```javascript
  db.tracks.createIndex({ track_genre: 1, popularity: -1, "audio_features.danceability": 1 })
  ```

* **ПІСЛЯ створення індексу (`explain`):**
  * `stage`: `"FETCH"` (вкладена стадія `"IXSCAN"`).
  * `indexName`: `"track_genre_1_popularity_-1_audio_features.danceability_1"`
  * `totalDocsExamined`: Дорівнює кількості повернутих документів.
  * *Що змінилося:* Стадія `SORT` зникла. Завдяки правильному порядку полів у індексі, база дістає дані вже відсортованими, а повне сканування замінилося на швидке перебирання дерева індексу (`IXSCAN`).

### Завдання 4.2. Складений індекс для фонового пошуку
Створено індекс для швидкого пошуку треків за критеріями відсутності explicit-контенту, високої інструментальності та низької мовленнєвої складової:
```javascript
db.tracks.createIndex({ explicit: 1, "audio_features.instrumentalness": 1, "audio_features.speechiness": 1 })
```
Вивід `explain()` підтвердив використання `IXSCAN` та цього індексу для фонових запитів.

### Завдання 4.3. Покривний запит (Covered Query)
**Запит:** ```javascript
db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } })
```
**Питання: Чи є цей запит покривним?**
**Відповідь:** **Ні.**
Хоча поля `track_genre` та `popularity` існують в індексі (база успішно робить `IXSCAN`), у запиті відсутня **проєкція**. За замовчуванням MongoDB повертає весь документ (з полями `_id`, `track_name` тощо). Оскільки цих полів немає в індексі, база змушена робити ресурсоємну стадію **`FETCH`** — читати фізичні документи з диска.

**Як виправити:** Щоб запит став покривним і зникла стадія `FETCH`, потрібно додати проєкцію:
```javascript
db.tracks.find(
  { track_genre: "pop", popularity: { $gte: 70 } }, 
  { _id: 0, track_genre: 1, popularity: 1 }
)
```
